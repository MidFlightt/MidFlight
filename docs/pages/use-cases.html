What each actor can do inside Midflight

Reaching coding agents

Midflight answers. It never speaks first.

A coding agent only takes in three things: what its user types, the replies to tool calls it makes, and context its host injects (such as Claude Code hooks). An MCP server can only answer calls. So every message from Midflight has to travel inside a reply to something the agent, or a hook acting for it, called. The design is built around that.

UC-01

Set up project & team

FR-01 · NFR-07 · NFR-09 · D16–D18
Primary actor
Integration Lead
Supporting
GitHub
Trigger
A team wants Midflight on one of its repositories.
Preconditions
None. Nothing is installed or self-hosted (D16).

Main success scenario

  1. The lead installs the public Midflight GitHub App on the repository.
  2. The lead adds Midflight to their AI client as a connector (one URL) and signs in with GitHub (D17).
  3. The lead asks their agent to create a project for the repository.
  4. Midflight checks the App is installed and the lead is a repo admin, creates the project with the lead as its lead, and returns a join code.
  5. The lead shares the join code with the team.
  6. Each teammate adds the same connector, signs in with GitHub, and joins with the code (UC-02).
  7. The lead assigns the plan's tasks to members (UC-03). Each change is audited.

Alternate & failure paths

  • 4aThe App isn't installed on the repository. Nothing is created; the reply links to the install page.
  • 4bThe lead isn't a repo admin. Nothing is created; the reply names the permission needed.
  • 6aA wrong or rotated join code is refused.
  • *aA member who isn't the lead tries a lead action and is refused (403).
  • *bThe lead removes a member or rotates the code; the member's calls are refused from then on.

Postcondition: Every member can perform only the operations their role allows, in their own projects only.

UC-03

Approve plan version

FR-02 · FR-10
Primary actor
Integration Lead
Trigger
The first plan, or a change such as adding currency to checkout-response.
Preconditions
UC-01 is done.
Includes
UC-08 when version > 1

Main success scenario

  1. The lead drafts the plan: requirements, tasks, and contracts with their fields, provider, and consumers.
  2. Midflight validates it. IDs must be unique, every contract needs one provider, and every reference must exist.
  3. Midflight shows the changes from the current version: requirement and contract IDs added, changed, or removed.
  4. The lead approves with a reason.
  5. Midflight stores an immutable new version, advances the project's coordination revision, and writes an audit event.
  6. For version 2 onward, Midflight runs UC-08 Propagate plan change.

Alternate & failure paths

  • 2aValidation fails. Midflight lists each problem and nothing is saved.
  • 4aSomeone approved another version first. The draft must be rebased on the newer version.
  • *aA developer or agent tries to approve and gets 403. A proposed requirement never replaces the approved plan.

Postcondition: All older versions stay readable. New claims must reference the current version.

Sequence

sequenceDiagram
    autonumber
    actor L as Lead
    participant API as Midflight API
    participant DB as DynamoDB
    participant W as Worker
    L->>API: submit plan draft v2 (adds currency)
    API->>API: check lead role, validate IDs and references
    alt invalid
        API-->>L: list of problems, nothing saved
    else valid
        API->>DB: read current version v1
        API-->>L: diff, checkout-response changed
        L->>API: approve with reason
        API->>DB: write v2 IF current is v1, bump coord_rev, audit, propagate job

            DB-->>API: ConditionalCheckFailed
            API-->>L: rebase the draft on the newer version
        else saved
            DB-->>API: ok
            API-->>L: plan v2 approved
            DB-->>W: stream event, propagate job (UC-08)
        end
    end
UC-13

Resolve escalation

FR-10 · FR-12
Primary actor
Integration Lead
Trigger
An open escalation from UC-12.
Preconditions
The escalation has evidence attached.

Main success scenario

  1. The lead opens the escalation. Example: T2 wants a tax-inclusive total while T1 excludes tax.
  2. Midflight shows the competing requirements, the claims involved, and the evidence.
  3. The lead picks one: clarify the plan (goes to UC-03), ask an agent to revise (its claim moves to needs_revision and it gets a directive), or dismiss the finding with a reason.
  4. Midflight records who decided and why, and keeps the original finding.
  5. Midflight re-checks the affected claims or commits.

Alternate & failure paths

  • 3aThe lead defers. The escalation stays open and affected approvals stay blocked.
  • *aA non-lead tries to resolve it and gets 403.

Postcondition: The audit trail links each resolution to the revalidation it caused.

UC-14

Monitor work & audit

FR-11 · FR-12 · NFR-06 · NFR-12
Primary actor
Integration Lead
Trigger
The lead opens the dashboard.
Preconditions
The lead is authenticated.

Main success scenario

  1. The dashboard shows the current plan version and each task: agent, branch, claim state, open findings.
  2. It lists directives with their delivery state: queued, delivered, acknowledged, rejected, or needs clarification.
  3. It shows verification per commit (passed, failed, needs review, incomplete) with a link to GitHub.
  4. It shows sync state, last good sync, and outstanding or failed jobs.
  5. The lead opens any item's timeline and sees the chain of reasons that produced it.

Alternate & failure paths

  • 2aA directive has stayed queued for a long time because the agent hasn't called. The lead can nudge the developer.
  • 4aA job is in the dead-letter queue. It's shown with its error and a retry action.
  • 4bState is stale. A banner explains that a GitHub check may still show an old result.

Postcondition: The lead can tell what needs attention without reading raw logs.

UC-02

Connect coding agent

FR-07 · D16 · D17
Primary actor
Developer
Trigger
The developer wants their agent to take part in a project.
Preconditions
The developer has the project's join code, or is its lead.

Main success scenario

  1. The developer adds the Midflight connector URL to their AI client: claude mcp add --transport http midflight <url>/mcp in Claude Code, or Add custom connector in Claude or ChatGPT.
  2. The client discovers that Midflight needs sign-in and opens the browser; the developer signs in with GitHub.
  3. The agent lists Midflight's tools and receives the instructions for planning checkpoints and reporting assumptions (D10).
  4. If new to the project, the agent calls join_project with the code.
  5. A check_in returns the developer's task, its requirements, and its contracts.

Alternate & failure paths

  • 2aSign-in is cancelled or fails. Midflight's tools stay unavailable.
  • 4aThe developer belongs to several projects. Tools ask which one, or take a project_id.
  • 5aNo task is assigned yet. The reply says so and asks the developer to tell the lead.
  • 5bMidflight is unreachable. The agent must not proceed as if anything were approved.

Postcondition: The agent reaches Midflight as its developer, in that developer's projects only.

UC-07

Check in

FR-07 · FR-06
Primary actors
Coding Agent, Developer
Trigger
A checkpoint the agent planned at a critical point of its task (D10: before implementing, before building on a contract or shared interface, when an assumption or its scope changes, before pushing), or a host hook acting for the agent.
Preconditions
UC-02 is done.
Replaces
get_task_context and get_directives

Main success scenario

  1. The agent, or its hook, calls check_in(T2).
  2. Midflight returns what changed since the last check-in: plan version, claim state, findings, new directives.
  3. Midflight marks the returned directives as delivered.
  4. If there are blocking findings or unacknowledged blocking directives, the reply tells the agent to pause or revise.
  5. Otherwise the agent continues.

Alternate & failure paths

  • 2aNothing changed. The reply is short: the current plan version and "no changes".
  • 2bA review is still running. The reply says pending, and the agent continues non-conflicting work without resubmitting.
  • 2cState is stale. The reply flags it and withholds new directives.
  • 2dThe agent asks about another person's task. It gets a read-only view of the contracts it consumes; anything else is 403 (Q3).
  • 5aThe agent has made a new assumption, or its scope has changed, since its last claim. It submits a revised claim with the updated assumptions (UC-06) and waits for the verdict before building on it.

Postcondition: The agent works from the current plan, not from its own conversation history.

    end
UC-04

Submit claim

FR-03 · FR-04 · NFR-01
Primary actor
Coding Agent
Trigger
The agent is about to start implementing a task.
Preconditions
An approved plan exists, and the task is assigned to this agent.
Includes
UC-05

Main success scenario

  1. The agent calls submit_claim with task, branch, base SHA, plan version, requirement IDs, expected files, provided and consumed contracts with field types, assumptions, and acceptance criteria.
  2. Midflight authenticates the caller and checks every reference.
  3. It saves the claim as pending together with a review job, in one write.
  4. It runs UC-05 Check claim in the background while the adapter waits.
  5. The adapter returns the verdict in the same call: approved, needs_revision, or human_review_required, with the agreed contracts, findings, proposed corrections, and any pending directives.
  6. If approved, the agent builds against the returned contract. Otherwise it revises through UC-06.

Alternate & failure paths

  • 2aAn unknown requirement or contract ID. The error lists the valid IDs and nothing is saved.
  • 2bThe claim cites an old plan version. The error points to the current one.
  • 2cThe task belongs to another agent: 403.
  • 2dThe claim omits interfaces or criteria. It is saved as a draft and the verdict asks for the missing detail before approval (D5). A task with no interfaces, like T3, declares no_interfaces: true instead (D12).
  • 5aThe review takes longer than the wait limit (~60 s). The call returns pending with a job ID, and the verdict arrives in the agent's next check_in.

Postcondition: No accepted claim is ever without a review job, and the agent never has to poll for its own review.

Sequence

sequenceDiagram
    autonumber
    participant A as Frederik's agent
    participant AD as MCP adapter
    participant API as Midflight API
    participant DB as DynamoDB
    participant W as Worker
    A->>AD: submit_claim(T2, consumes checkout-response.total_cents:int)
    AD->>API: POST /projects/{pid}/claims
    API->>API: authenticate, validate references
    alt unknown ID or old plan version
        API-->>AD: 400 with valid IDs or current version
        AD-->>A: fix and resubmit
    else valid
        API->>DB: one write, claim (pending) plus review job
        API-->>AD: claim_id, job_id
        DB-->>W: stream event, review job

        W->>DB: save verdict
        loop every 2 s, up to about 60 s
            AD->>API: GET /jobs/{jid}
        end
        alt verdict ready
            API-->>AD: approved, contract, pending directives
            AD-->>A: approved, build against checkout-response v1
        else wait limit reached
            AD-->>A: pending, verdict comes with next check_in
        end
    end
UC-05

Check claim

FR-04 · NFR-02 · NFR-03 · NFR-05
Kind
Included by UC-04 and UC-06
Supporting
AI Reviewer
Trigger
A review job
Extended by
UC-12

Main success scenario

  1. The worker loads the approved plan and all active claims at coordination revision N.
  2. Rules run first: stale version, missing references, contract field or type mismatch (total vs total_cents), and file overlap (recorded as info only).
  3. The worker sends the free-text assumptions and related claims to the AI Reviewer.
  4. It checks the reviewer's reply against the findings schema and confirms every cited ID exists.
  5. It decides approved or needs_revision with evidence and a proposed fix.
  6. It saves the decision only if the coordination revision is still N, and writes an audit event.

Alternate & failure paths

  • 5aThe finding is a requirement conflict or the reviewer is unsure. Goes to UC-12.
  • 4aThe reply is malformed or times out. No approval. The job retries a bounded number of times, then the result is review incomplete.
  • 6aThe revision changed because another claim landed. Re-run from step 1, with a bounded number of attempts.
  • *aThe same job is delivered twice. Midflight produces one decision and one audit event.

Postcondition: Two conflicting claims can never both be approved from an outdated snapshot.

Sequence

sequenceDiagram
    autonumber
    participant DB as DynamoDB
    participant W as Worker
    participant R as AI reviewer
    DB-->>W: review job for claim T2 rev 1
    W->>DB: read plan v1 and active claims at coord_rev 7
    W->>W: rules, version, references, contract fields, file overlap
    W->>R: assumptions and related claims (no tools)
    alt malformed reply or timeout
        R-->>W: invalid
        W->>W: never approve, retry (bounded), then review incomplete
    else valid findings
        R-->>W: findings JSON
        W->>W: validate schema, check every cited ID exists
        alt requirement conflict or reviewer unsure
            W->>W: UC-12 Escalate to lead
        else decision reached
            W->>DB: save verdict IF coord_rev is 7, set 8
            alt another claim landed first
                DB-->>W: ConditionalCheckFailed
                W->>W: rerun from the snapshot read (bounded)
            else saved
                DB-->>W: ok, audit event written
            end
        end
    end
UC-06

Revise or withdraw claim

FR-03
Primary actor
Coding Agent
Trigger
A finding, a directive, or the agent learning more.
Preconditions
The claim exists and belongs to this agent.
Includes
UC-05 for revisions

Main success scenario

  1. The agent submits a revision with the same claim ID, for example T2 now consuming total_cents:int.
  2. Midflight keeps the previous revision and its findings and stores the new one as pending.
  3. Midflight runs UC-05 and returns the verdict in the same call, as in UC-04.

Alternate & failure paths

  • 1aThe agent withdraws the claim, or closes an approved claim when the work is done (D11). It stops reserving work and is excluded from other claims' checks.
  • 1bA different agent tries to revise it: 403.

Postcondition: The claim history shows every revision and why it changed.

UC-09

Acknowledge directive

FR-06 · FR-07
Primary actor
Coding Agent
Trigger
A directive arrives inside any Midflight reply: submit_claim, check_in, or a hook-run check_in.
Preconditions
A current (not superseded) directive exists for the task.

Main success scenario

  1. The agent reads D-42: "display currency next to the total (plan v2)".
  2. It treats this as information to consider and never runs it as a command.
  3. It calls acknowledge_directive(D-42, acknowledged, note).
  4. The lead sees the acknowledgment on the dashboard.
  5. The agent revises its claim through UC-06.

Alternate & failure paths

  • 3aThe agent replies needs_clarification. The question appears for the lead.
  • 3bThe agent replies rejected with a reason, and the lead is alerted.
  • 1aThe directive was superseded by v3. Only the replacement is delivered.

Postcondition: Acknowledged means received, not implemented. Only UC-10 proves implementation.

UC-16

Gate push on directives

FR-07
Primary actor
Coding Agent (via git push)
Trigger
A push from a clone with the Midflight pre-push hook installed.
Preconditions
UC-02 step 4 is done.

Main success scenario

  1. The agent runs git push.
  2. The pre-push hook calls check_in for the branch's task.
  3. The claim is approved for the current plan version and no blocking directive is unacknowledged.
  4. The push goes through.

UC-08

Propagate plan change

FR-05 · FR-06 · NFR-02
Kind
Included by UC-03
Trigger
Plan version N > 1 is approved.
Extended by
UC-12 (unclear impact), UC-15 (stale)

Main success scenario

  1. Midflight compares version N−1 with N and finds that checkout-response changed.
  2. It looks up the contract's provider (T1) and consumers (T2), plus any tasks implementing a changed requirement.
  3. Each affected active approval goes back to pending for revalidation.
  4. Midflight creates one directive per affected task, with reason, changed IDs, and requested adjustment, in state queued.
  5. It supersedes that task's older directives that are still queued or delivered.
  6. T3 has no link to the change, so it gets nothing.
  7. Each directive is delivered inside its recipient's next Midflight reply (UC-07, UC-04, or UC-16). Midflight can't interrupt a running agent.

Alternate & failure paths

  • 2aThe impact is unclear, such as a requirement text change with no contract link. Goes to UC-12 instead of guessing.
  • 4aState is stale. Directives are held until fresh (UC-15).
  • *aThe event is processed twice. Each (plan version, task) pair still gets only one directive.

Postcondition: No affected task keeps an approval based on the old version.

UC-12

Escalate to lead

FR-04 · FR-05 · FR-09 · FR-10
Kind
Extends UC-05, UC-08, UC-10
Extension points
Conflicting human requirements · unclear finding · unclear impact · branch edits its own contract tests

Main success scenario

  1. Midflight creates an escalation with the competing requirements, the claims or commit involved, and the evidence.
  2. Affected claims go to human_review_required, or the commit check goes to action_required.
  3. Affected approvals and passes stay blocked while the escalation is open.
  4. The escalation appears on the lead's dashboard, waiting for UC-13.

Rule

UC-10

Verify pushed commit

FR-08 · FR-09 · NFR-08 · NFR-10
Primary actor
GitHub (signed webhook)
Supporting
AI Reviewer
Trigger
The contract-test workflow (contract.yml) finishes for a PR's head commit: workflow_run, action completed (D4).
Preconditions
The PR's branch is linked to a claim.
Includes
UC-11
Extended by
UC-12, UC-15

Main success scenario

  1. Midflight checks the webhook signature, drops duplicate delivery IDs, saves a job, and replies 202.
  2. The worker fetches the PR's current head and confirms it matches the event's SHA.
  3. It fetches the diff, the relevant file contents, and the contract-test results for that exact SHA.
  4. Rules run: undeclared files, required contract fields present, test result. Edited contract tests or workflows go to UC-12.
  5. The AI Reviewer adds semantic findings, which are validated as in UC-05.
  6. Right before publishing, the worker re-checks that the head SHA and plan version haven't changed.
  7. It runs UC-11 Publish verify check.

Alternate & failure paths

  • 1aThe signature is invalid: 401 and nothing is stored.
  • 4aThe agent said "done" but total_cents is missing. Result is failure with evidence, plus a correction directive to the agent.
  • 3aThe diff is truncated or test results are missing. Result is incomplete, never success.
  • 6aA newer commit or plan arrived. The result is discarded and a new job runs.
  • 2aGitHub returns an error or rate limit. Goes to UC-15.
  • 5aThe diff contains instructions aimed at the AI. They're treated as data, may be noted as info, and don't change the outcome.

Postcondition: The result is tied to one commit, one claim revision, and one plan version.

UC-15

Mark stale & reconcile

FR-08 · NFR-04 · NFR-06
Kind
Extends UC-10 and UC-08
Extension point
GitHub 5xx, rate limit, or timeout

Main success scenario

  1. Midflight marks the project's sync state stale with a timestamp.
  2. It holds directives and approvals that depend on GitHub data.
  3. It retries after the rate-limit reset time, a bounded number of times.
  4. On recovery it re-fetches PR heads, re-runs affected verifications, and re-publishes checks.
  5. It clears the stale flag and writes an audit event.

Alternate & failure paths

  • 3aRetries run out. The job goes to the dead-letter queue and shows on the dashboard (UC-14).

Limitation: During an outage GitHub may still show an old green check. The dashboard says so.

Review questions

Where the open questions stand

Decided and default answers are logged in docs/design-decisions.md.

  • New agent tools: D3 (default)submit_claim (waits for the verdict), check_in, and acknowledge_directive replace get_task_context and get_directives. FR-07 and the architecture doc are updated.
  • Pre-push hook when Midflight is down: D8 (default)Warn and allow. The GitHub check still verifies the commit.
  • Incomplete claims: D5 (default)Saved as draft; no approval until interfaces and criteria are given.
  • Verification trigger: D4 (default)Starts when the contract-test workflow completes, so the evidence already exists.
  • Canonical plan change: D2 (default)currency, used throughout.
  • Developers submitting claims by hand: open (Q1)Default: agents only. If developers should also submit claims, UC-04 gets a second actor.
  • Agents accepting proposed contracts: open (Q2)Default: no. Contracts change only through the lead (UC-03) or an escalation (UC-13).
  • Cross-task visibility (UC-07 · 2d): open (Q3)Default: a read-only view of the contracts a task consumes; anything else is 403.
  • Consistency pass: D11–D15 (default)Closing a claim (status: closed), claims with no interfaces (no_interfaces), directive sources and dedupe, escalation transitions, and one REST path table in docs/domain.md.
